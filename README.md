# ระบบเทียบเคียงสมรรถนะและพิจารณาเทียบโอน TPQI กับรายวิชาอาชีวศึกษา

COMPASS รุ่น 0.2 | 11 กันยายน 2569 | แอปพลิเคชันสำหรับทดลองงานจริงและตรวจรับ

หลักการ: **เอกสารต้นฉบับมาก่อน → เทียบข้อกำหนดเป็นรายข้อ → แสดงหลักฐานทั้งสองฝั่ง → ผู้เชี่ยวชาญยืนยัน → ผู้มีอำนาจพิจารณาเทียบโอนรายบุคคล**

พัฒนาเว็บภาษาไทยด้วย React / vinext, ฐานข้อมูล D1 และคลัง PDF R2 แล้ว หน้าตาโทนขาว–เขียวอมฟ้า ใช้มิติ 3D กับภาพประกอบและปุ่มอย่างพอดี รองรับมือถือ คีย์บอร์ด และลดภาพเคลื่อนไหวตามการตั้งค่าผู้ใช้

ทำงานได้: ค้นรายวิชาและมาตรฐานจริง, สร้างตาราง UoC/EoC/PC พร้อมหลักฐาน, บันทึกฉบับและ SHA-256, ส่งผู้เชี่ยวชาญสองบทบาท, รับรองและเผยแพร่ตามสิทธิ์, จัดเก็บ PDF ส่วนตัว, รับคำร้อง, พิมพ์รายงาน 4 มุมมอง และส่งออก CSV ไม่มีผล mapping หรือผลรับรองสมมติในข้อมูลเริ่มต้น

บัญชีผู้ดูแลเริ่มต้น: `itp@utc.ac.th` ใช้ตัวตนที่ยืนยันผ่าน Sites ไม่ได้สร้างรหัสผ่านให้ผู้ใช้ การเพิ่มผู้เชี่ยวชาญในแอปไม่ได้เปลี่ยนสิทธิ์เข้าชมเว็บไซต์ชั้นนอกหรือส่งอีเมลเชิญ

รุ่นนี้ยังไม่ออกคำตัดสินเทียบโอนหน่วยกิต ต้องพัฒนาขั้นอนุมัตินโยบายและการประเมินบุคคลให้ครบก่อนเปิดใช้ ข้อกำหนดที่เสนอในเอกสารออกแบบไม่ใช่ระเบียบที่ประกาศใช้แล้ว ดู [สถานะการพัฒนาและข้อจำกัด](docs/IMPLEMENTATION.md)

## ผลจับคู่ทั้งคลัง

เปิด **ผลจับคู่ทั้งคลัง** (`/automatic`) เพื่อดูเปอร์เซ็นต์และคู่มาตรฐานที่คำนวณไว้แล้ว ไม่ต้องเลือกรายวิชาเพื่อเริ่ม inference และไม่ต้องดาวน์โหลดโมเดล ค้น/กรองผล เปิดคู่มาตรฐานทางเลือก ดูตาราง UoC/EoC/PC และพิมพ์รายงานได้ทันที

ผลเป็นข้อเสนอจากโมเดล E5 จริง โดยใช้เอกสารอ้างอิงก่อนคะแนนข้อความ ผู้จัดทำสามารถนำผลที่พร้อมไปจัดทำหลักฐานรับรองในกระบวนการเดิม ทุกข้อยังรอผู้เชี่ยวชาญ ไม่มีการรับรองหรืออนุมัติหน่วยกิตอัตโนมัติ

รายละเอียดการคำนวณ ขอบเขต snapshot และวิธีดูแลข้อมูล: [BULK_MAPPING.md](docs/BULK_MAPPING.md)

การสร้างคู่เฉพาะเพิ่มเติมยังมีที่ `/automatic/new` และ Embedding แบบรายงานเดิมยังใช้ได้ในแท็บของงาน: [EMBEDDING_MATCHER.md](docs/EMBEDDING_MATCHER.md)

## ใช้งานและพัฒนาบนเครื่อง

ต้องใช้ Node.js 22.13 ขึ้นไป

```bash
npm ci
cp .env.example .env.local
npm run dev
```

เปิด `http://localhost:3000` หากต้องการทดสอบด้วยบัญชีผู้ดูแลบนเครื่องของตนเอง ให้กำหนด `LOCAL_DEV_EMAIL=itp@utc.ac.th` ใน `.env.local` ก่อนเริ่มเซิร์ฟเวอร์ ค่านี้ทำงานเฉพาะ development บน localhost และไม่ถูกใส่ใน production build

```bash
npm run check
python3 scripts/verify_evidence.py
```

`check` ตรวจ TypeScript, ESLint, ทดสอบกฎ 28 กรณี และสร้าง production build การทดสอบ HTTP เพิ่มเติมใช้ `node scripts/test-local-api.mjs` และ `node scripts/test-auto-api.mjs` เมื่อ local server ทำงานและตั้ง `LOCAL_TEST_KEY` ใน `.dev.vars` สคริปต์สร้างข้อมูลทดสอบในเครื่องเท่านั้นและลบแถวทดสอบเมื่อจบ ไม่รวมข้อมูลนี้ในรุ่นที่เผยแพร่

## เอกสารสำหรับเริ่มงาน

1. [แบบระบบและการใช้งาน](docs/SYSTEM_DESIGN.md) — ขอบเขต หน้าบ้าน หลังบ้าน สิทธิ์ ขั้นตอน และสถาปัตยกรรม
2. [หลักเกณฑ์ mapping และการรับรอง](docs/MAPPING_POLICY.md) — ลำดับหลักฐาน ตารางเทียบ การนับความครอบคลุม และเงื่อนไขห้ามสรุปผล
3. [ผลตรวจแหล่งข้อมูลจริง](docs/DATA_SOURCE_AUDIT.md) — API ที่ตรวจสอบแล้ว ตัวอย่างข้อมูล ข้อจำกัด และแนวทางนำเข้า
4. [แบบข้อมูลและสัญญา API ภายใน](docs/DATA_MODEL.md) — หน่วยข้อมูล ความสัมพันธ์ เวอร์ชัน และข้อบังคับธุรกรรม
5. [หน้าจอและแบบรายงานพิมพ์](docs/UX_AND_REPORTS.md) — ลำดับการทำงาน wireframe ตารางเทียบ และเอกสาร 6 ประเภท
6. [แผนพัฒนาและเกณฑ์ตรวจรับ](docs/DELIVERY_PLAN.md) — งานเรียงตามความสำคัญ การทดสอบ และเงื่อนไขพร้อมใช้งาน

ข้อมูลตั้งต้นใช้เว็บไซต์ที่ผู้ใช้ระบุโดยตรง ได้แก่ [มาตรฐาน](https://dles.vec.go.th/standards) และ [รายวิชา](https://dles.vec.go.th/subject/) พร้อมตามกลับเอกสารของเจ้าของมาตรฐาน ไม่ถือผลแนะนำความคล้ายหรือป้ายยืนยันจากระบบอื่นเป็นการรับรองในระบบนี้

## หลักฐานการสำรวจ

เก็บ JSON และ PDF ที่อ่านได้จริงใน `docs/evidence/` พร้อม URL เวลาที่ดึง และ SHA-256 ใน `manifest.json` เป็นตัวอย่างขนาดเล็ก ไม่ใช่สำเนาฐานข้อมูลทั้งหมด

```bash
python3 scripts/capture_sources.py
python3 scripts/verify_evidence.py
```

คำสั่งแรกดึงตัวอย่างสาธารณะและสร้างโฟลเดอร์ใหม่ทุกครั้ง คำสั่งที่สองตรวจหลักฐานล่าสุดแบบออฟไลน์ สคริปต์นี้ไม่มีการเขียนหรือยืนยันผลบนเว็บไซต์ต้นทาง และยังไม่ใช่ตัว sync สำหรับ production
